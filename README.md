# Aspire + React + Spring Boot + ASP.NET Core + Go: secure, asynchronous polyglot starter

> **Spring Boot owns identity. ASP.NET Core owns todos. Go processes them asynchronously. RabbitMQ delivers the work, Redis tracks transient
> state, PostgreSQL is the system of record. React consumes Spring and ASP.NET. Aspire orchestrates everything.**

```
                                  ┌───────────────┐
                                  │ React (Vite)  │  talks only to Spring and ASP.NET (same origin via proxy)
                                  └───────┬───────┘
                      /api/auth, /api/users, /api/admin/users        /api/todos, /api/admin/todos
                    ┌─────────────────────┴───────────┐       ┌──────────────────┴──────────────┐
                    ▼                                 │       ▼                                 │
             ┌──────────────┐   JWKS (public keys)    │ ┌──────────────┐                        │
             │ Spring Boot  │◄────────────────────────┼─┤ ASP.NET Core │                        │
             │   Identity   │                         │ │   Todo API   │                        │
             └──────┬───────┘                         │ └──┬────────┬──┘                        │
                    ▼                                 │    ▼        │ outbox ──► RabbitMQ       │
                 authdb ◄──────── PostgreSQL ────────►│ tododb      │            todo.events    │
                                                      │             ▼               │           │

                                                      │                      ┌─────────────┐    │
```

### Demonstration scenario (5 minutes)

1. Open `frontend`, register, sign in. Go to **Todos** → **New todo** "Learn Go concurrency".
2. The todo appears as **Queued** immediately, then **Processing**, then **Waiting for release** (the page polls while anything is in flight).
3. In RabbitMQ's UI (dashboard link) watch `todo.processing`/`todo.status`. In `todo-worker` logs see the `job started` / `job finished` lines.
4. Release it: either wait for the worker's timer (`Worker:ReleaseInterval`, **1 min** in dev, 5 min default) or sign in as the admin (`admin@example.com`), open **All todos** and press **Release** (or **Release all waiting**).
5. The todo becomes **Completed** by itself. A normal USER cannot release anything: the API answers 403.

**Concurrency demo**: `python scripts/demo.py --url <frontend-url> --count 20 --release` (admin password in the env var `DEMO_ADMIN_PASSWORD`)
creates 20 todos, prints every transition and shows them processed in bursts of at most `WORKER_CONCURRENCY` (5). Sample run on this repo:
`QUEUED=20 → PROCESSING=5 → … → WAITING_RELEASE=20` in 16 s (20 × 4 s ÷ 5), then a USER release attempt → 403, ADMIN release-all → all `COMPLETED` in ~1 s.

## Todo processing design

**Creation** (`POST /api/todos`): authenticate → authorize → validate → in **one DB transaction** insert the todo (`QUEUED`) **and** an outbox row
(`TodoCreated`) → return the todo with `processingStatus: QUEUED`. A background publisher sends outbox rows to RabbitMQ with publisher confirms.

**Consistency trade-off (transactional outbox).** Writing to PostgreSQL and publishing to RabbitMQ cannot be one atomic operation. A naive
"save, then publish" loses the message if the broker is down or the process dies in between. The outbox makes the *message* part of the same
transaction as the *todo*, so they exist together or not at all, and the publisher retries until the broker confirms. The cost: delivery is
**at-least-once** (a crash between publish and "mark published" re-sends), so every consumer is idempotent; ordering is per-queue, not global; and
published outbox rows are not purged yet (see limitations). That is the right price for a learning system with a single database and broker.

**Who owns what.** The worker never writes to the todo database. It *reports* `TodoStatusChanged` events; the Todo API validates each transition
(forward-only state machine, atomic guarded `UPDATE`) and persists it. Admin actions (`release`, `release all`, `retry`) are API endpoints that
authorize an ADMIN **first** and then publish a command through the outbox; the worker only trusts commands that arrive through the broker boundary.

| Endpoint (ASP.NET Core) | USER | ADMIN |
|---|---|---|
| `POST/GET/PUT/PATCH/DELETE /api/todos…` own todos (response includes `processingStatus`) | ✅ | ✅ (plus any todo by id) |
| `GET /api/admin/todos` (all todos + worker/attempt metadata, filter by user) | ❌ 403 | ✅ |
| `POST /api/admin/todos/{id}/release`, `POST /api/admin/todos/release` | ❌ 403 | ✅ 202 (409 if not waiting) |
| `POST /api/admin/todos/{id}/retry` (FAILED → QUEUED + new message) | ❌ 403 | ✅ 202 (409 if not failed) |

Details of the contract and topology: [`messaging/README.md`](messaging/README.md). Worker internals: [`todo-worker/README.md`](todo-worker/README.md).

## Failure handling at a glance

| Failure | What happens |
|---|---|
| RabbitMQ down | API still accepts todos (outbox rows wait; `/api/health` reports `Degraded` if they pile up); worker and API reconnect with backoff and drain |
| Redis down | worker stops taking work (`/ready` 503), messages stay in RabbitMQ; resumes when Redis returns; Redis is never the source of truth for undelivered work |
| PostgreSQL down | status reports are nacked with requeue and retried; the outbox publisher retries; the API returns errors for requests that need the DB |
| Worker crash | unacked messages are redelivered; the dead worker's lock lease expires; another attempt completes the job |
| Processing error/timeout | up to 3 retries through delay queues (5 s, 30 s, 2 min), then `FAILED` + dead-letter queue; an admin can **Retry** |
| Malformed message | straight to the dead-letter queue (never retried forever, never blocks the queue) |

## Identity, tokens and authorization (Phases 1-2, unchanged)

* **Spring Boot** is the only identity provider: registration, login, Argon2id passwords, 10-minute RS256 access tokens, rotating refresh tokens in HttpOnly
  SameSite=Strict cookies (hashed at rest, reuse ⇒ session revoked), lockout and rate limiting, RBAC (`USER`, `ADMIN`), JWKS at `/.well-known/jwks.json`.
* **Token contract** (`iss=auth-api`, `aud=[auth-api, todo-api]`, `sub`=immutable user id, `email`, `roles[]`): the Todo API validates signature (RS256 pinned),
  issuer, audience, lifetime, and requires a GUID `sub`; it never calls Spring per request and holds no secret.
* **Todo authorization**: policies (`Todo.CreateOwn/ReadOwn/UpdateOwn/DeleteOwn`, `Todo.ReadAll/UpdateAll/DeleteAll`, `Todo.Release`, `Todo.Retry`) plus an ownership handler; a todo
  you may not access is **404**, indistinguishable from a missing one (no IDOR probing). The owner is never client input (unknown body fields → 400).
* **React** keeps the access token in memory; all UI permission checks go through `useAuthorization()` / `<RequireRole>` / `<RequirePermission>` / `<ProtectedRoute>`
  (capabilities `todos:release`, `todos:retry` … derived centrally). That is UX only: every API re-checks.

## Security notes specific to Phase 3

* The worker has **no authentication system and no public API**. It trusts messages only through the broker; admin authority is decided by the Todo API (JWT roles) *before* a release command is published, and the command records the admin's id for audit.
* Broker credentials are the trust boundary: anyone who can publish to `todo.events` can forge messages. In this starter all services share one broker user (`app`, password generated by Aspire, only its hash in the generated definitions). Use one user per service with restricted permissions in production.
* Status messages are validated before use (known status, owner id must match the todo, forward-only transitions); failure text from the worker is sanitized and length-bounded (`processing failed`, `processing timed out`), never raw exception text; the DLQ keeps the original message plus the broker's `x-death` history.
* Messages carry identifiers only; logs carry ids, never tokens or todo content.

## Aspire AppHost

`AddPostgres` (+`authdb`, `tododb`, pgAdmin); `AddRabbitMQ("messaging")` with the management plugin, the topology file bind-mounted (merged with the generated broker user at startup);
`AddRedis("redis")` with persistence (plain TCP in dev via an experimental opt-out of Aspire's dev certificate); Spring as an executable (`mvnw spring-boot:run`, OTel Java agent);
`AddProject<Projects.TodoApi>` (`WithReference(tododb)`, `WithReference(messaging)`, JWKS location from the Spring endpoint); the Go worker as an executable (`go run ./cmd/worker`,
`PORT` from Aspire, RabbitMQ/Redis host, port and credentials injected as environment variables, tuning from `appsettings.Development.json` → `Worker:*`); `AddViteApp` with `BACKEND_URL` and `TODO_API_URL`.
Dependencies are expressed with `WaitFor`; health checks: Spring `/actuator/health/readiness`, Todo API `/api/health`, worker `/ready` (needs RabbitMQ **and** Redis).

## Known limitations

* **Processing is simulated** (`SimulatedProcessor`: sleeps `PROCESS_DURATION`, fails with probability `PROCESS_FAIL_RATE`). Replace `worker.Processor` with real work; the concurrency, retry, DLQ and release machinery is real.
* If Redis loses its data (not just availability), todos already `WAITING_RELEASE` in PostgreSQL have no entry in the release queue and wait until an admin retries or a reconciliation job is added. Persistence is enabled in dev to reduce this.
* Outbox rows are never deleted; add a retention job. Retry backoff lives in `definitions.json` (fixed per tier).
* One shared broker user and one Postgres superuser in dev; no per-service least-privilege roles yet.
* Telemetry: the Go worker emits structured logs only (no traces/metrics yet); the Spring and Todo API telemetry flow to the dashboard.
* `go run` compiles on every start (slow first start); the AppHost downloads the OTel Java agent unpinned; plain HTTP between local processes (dev only).
* The Todo API uses the ports from `launchSettings.json` (5229/7148); pgAdmin reports `Unhealthy` in `aspire describe` although it is usable (not investigated); the admin table scrolls horizontally on narrow screens.
* Forgot/reset password screens are placeholders (no email provider). Pre-Phase-3 todos were backfilled as `COMPLETED` by the migration.

## Recommended Phase 4

1. Real processing in the worker (and pass an OpenTelemetry trace context through the messages so one trace spans React → API → RabbitMQ → Go).
2. Per-service broker/DB credentials, TLS for AMQP/Redis/JWKS, and secrets from a vault; pin and checksum the OTel agent.
3. Outbox purge + a reconciliation job that re-queues todos stuck in a state longer than expected (also covers Redis data loss).
4. Server-sent events (or WebSocket) instead of polling for status updates.
5. CI (build, all four test suites, container publishing via Aspire), then the extra services the roadmap mentions.
